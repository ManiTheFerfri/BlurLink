# BlurLink V2 — design

Status: **approved in design review (chat), 2026-09-12.** Not implemented.
Related: `docs/architecture.md`, `docs/packet-research.md`, `SECURITY.md`,
`TODO.md` (the V1 work log), `docs/superpowers/specs/2026-09-11-host-side-rule-design.md`.

This checkout is not a git repository, so this document is uncommitted. Making
it the first commit is part of milestone M0 (§9).

## 1. Context: what V1 is, and what the audit found

V1 exists and works, but it has never been shown to do the thing it is for.

**What is real and verified** (re-checked 2026-09-12, not taken from `TODO.md`):

- Four projects — `Contracts` (IPC, config, profile schemas), `Core`
  (validation, filter builders, adapters, routing, rate limiting, diagnostics,
  logging), `Desktop` (WPF MVVM), `Net` (C++20 WinDivert helper: bridge, host
  session, host engine/roster/classify, announce codec, IPC server).
- `dotnet test` on the solution: **220 passed, 0 failed, 0 skipped**. Native
  suite green under `ctest`. Scripts parse clean.
- Two WinDivert sessions proven against a real driver on one machine with
  synthetic peers: 42 checks (`scripts/test-e2e.ps1`); 45 live interop checks
  (`scripts/test-interop.ps1`).
- Real game evidence: the 24-byte discovery query and the 160-byte host answer,
  both captured from live Blur; the answer's envelope confirms host mode's two
  load-bearing assumptions; the answer embeds **two** of the host's endpoints.
- Packaging: a ~3.5 MB framework-dependent single-file portable, with the helper
  and WinDivert embedded, SHA256-pinned, and staged on first launch.

**What the audit found missing or weak, ranked:**

1. **No version control.** No repository, no history, no tags, and a CI workflow
   that can therefore never fire.
2. **The central promise is unproven.** "The lobby appears over the tunnel" has
   never been observed with two machines. Everything proven is BlurLink's own
   logic against the real driver with synthetic peers on one box.
3. **Not shippable to a stranger.** Unsigned, no installer, no update path, a
   .NET Desktop Runtime prerequisite, x64 only, and a first run that meets
   research mode rather than a working configuration.
4. **The elevated harness is manual-only**, so the code path that produced both
   severe V1 bugs (the WinDivert shutdown flags, the recursive-lock deadlock) has
   no automated coverage.
5. **Deliberate V1 ceilings:** one port, IPv4 only, no payload rewrite, the
   adapter picker validated but unused in the filter, the documented `/23`
   `.255` refusal caveat.
6. **Desktop debt:** `JoinViewModel` is 1,261 lines against Host's 523 and
   Settings' 398; session state, helper JSON and user-facing text are tangled
   together; UI verification is XAML-parse and binding smoke tests only.
7. **Support story:** no crash capture, no diagnostic bundle, no telemetry by
   design — a bug report means walking someone through `helper.log`.
8. **Doc drift is proven, not theoretical:** the retracted "a hosting Blur is
   silent" claim lived in `README.md`, `TODO.md` and `docs/packet-research.md`
   simultaneously, and a shipped-versus-harness default was ambiguous in
   `TODO.md`.

## 2. Goals

| # | Goal | Why it is a goal |
|---|---|---|
| G1 | **The tunnel claim is proven** with two-machine evidence recorded the way the packet research already is, and each V1 open question is closed or explicitly marked open with the reason | Everything else is downstream of this; the product does not yet do what its README says |
| G2 | **Every automatable check runs in CI**, including the driver harness if it can, and docs cannot silently contradict the code | The most dangerous code is currently the least automatically checked |
| G3 | **A stranger installs it and gets a lobby**: guided first run, a shipped evidence-backed profile, plain-language status, one-click support bundle | "Research mode by default" and raw counters are the two things that make V1 unusable by anyone but its author |
| G4 | **The surface is rebuilt** on Avalonia 12 / .NET 10 LTS over one session state model | The features in G3 are state-model problems wearing UI clothes; the current shell makes them hard to build correctly |

## 3. Non-goals (V2)

- **No payload rewriting**, unless the decision gate in §5.6 opens on evidence,
  and then only with explicit per-session consent.
- **No code signing, no MSIX, no Store, no auto-update.** Deliverable is an
  unsigned portable exe plus a zipped release; the SmartScreen warning is
  documented as a known cost. winget listing is deferred.
- **No cross-platform shipping and no portability work** beyond a thin seam. The
  capability is irreducibly Windows: WinDivert and Blur are both Windows-only.
- **No telemetry, no accounts, no backend, no relay, no VPN, no NAT traversal.**
  V1's promises stand unchanged.
- **Blur only.** No generic multi-game profiles. IPv4 only. One session at a
  time. English only.
- **No driver-technology research.** WinDivert 2.2.2 stays.
- **`Core`, `Contracts` and `Net` are not rewritten.** The native helper, the
  packet codec, the filter builders and `tools/hostsim` are unchanged except
  where a goal explicitly requires it (`ifIdx` term, §7.5).
- **Blur's own configuration is never modified.** No firewall-rule editing, no
  route changes, no registry edits to the game.

## 4. Decisions taken in review

| # | Decision | Rationale |
|---|---|---|
| D1 | UI: **Avalonia 12 on .NET 10 LTS**, target `net10.0-windows` | .NET 8 leaves LTS in Nov 2026; Avalonia 12 is the current line with a rewritten renderer, first-class NativeAOT docs, and a headless test platform. WinUI 3's deployment model fits a driver-helper tool badly; WPF cannot ever be trimmed or AOT'd (`NETSDK1168`) |
| D2 | Shape: **re-cut the desktop around one session state model** (not a port, not a greenfield rewrite) | The tested core is worth keeping; the debt is concentrated in the shell and in status plumbing, which is exactly what the G3 features need |
| D3 | **Windows-only shipping**, no portability spend | Avalonia is chosen for UI quality, the AOT flavor and CI testability, not for other operating systems |
| D4 | **Evidence-gated payload rewrite** (§5.6) | Reopening a safety promise requires evidence and an explicit gate, not enthusiasm |
| D5 | **Driver harness: try GitHub-hosted runners first** | The code path that produced both severe bugs deserves automated coverage; the runners are already administrators, and one experiment settles whether the driver installs there |
| D6 | **Unsigned for now**, SmartScreen warning documented | Signing is a cost and an identity question; it must not gate the evidence or engineering work |
| D7 | **Public GitHub repo, tagged releases** with the portable build | Matches what the project already is (MIT, `SECURITY.md`, third-party notices, a GitHub-shaped CI file); carries a mandatory privacy scrub (§8.1) |
| D8 | **Zero new runtime dependencies.** No DI container, no MVVM toolkit | The app has none today; the composition root and the existing hand-rolled base class are sufficient, and fewer dependencies keep the AOT/trimming path simple |
| D9 | **Strict sequence**: evidence → engineering → surface → release | Chosen in review: the evidence can change what is worth building |
| D10 | **Slim framework-dependent stays the deliverable**; NativeAOT single-file is spiked as the no-runtime flavor | The release must never depend on the AOT spike succeeding |
| D11 | **Reply-shape validation ships observe-only** | Refusing a reply the product does not fully understand would break discovery; report first, enforce only after a second independent capture agrees |
| D12 | **Legacy `-Full` / `-Sfx` builds retired** if the AOT spike delivers a usable no-runtime flavor | The 140 MB self-contained path exists only because WPF cannot be trimmed; that reason disappears with Avalonia |

## 5. The evidence plan (milestone M1)

### 5.1 Questions, in dependency order

| # | Question | Instrument | Why it matters |
|---|---|---|---|
| a | Does the player's forward reach the host **over the tunnel** at all? | Host mode's `forwards heard` counter plus the helper log | This is host mode's premise. Zero means the problem is upstream of everything BlurLink does, and no UI wording may imply otherwise |
| b | Which of the **two endpoints the host's own reply embeds** does the player's Blur dial — the physical LAN address (dead across the tunnel) or the overlay address (reachable)? | Host captures its own reply and reads both embedded endpoints off it; player then watches for those two addresses on the gameplay port `3074` | The single fact that decides whether V1's "no payload rewrite, ever" promise has to be reopened |
| c | Does the **lobby appear**, and does a **join complete**? | Both screens, screenshots plus logs | The product's actual claim |

### 5.2 Instruments

- Host: Host mode (as built) with its counters, its dashboard, and `--log-file`
  so the log survives the console closing; plus a capture of its own outbound
  discovery replies, because the two addresses the player might dial are only
  knowable from the host's own reply payload. The addresses quoted in this
  section (`192.168.1.116:3074`, `10.88.14.114:3074`) are the 2026-09-12
  session's; every future session reads its own off that capture before watching
  the player.
- Player: the bridge, its counters, and a capture filtered to the gameplay port
  and the two addresses read off the host's reply.
- **Clock correlation.** Both machines record wall-clock timestamps and their UTC
  offset at session start, so "the reply left the host at T" can be matched
  against "nothing arrived at T±2 s". Without this, the session produces two
  unlinkable logs and the answer to question (a) stays soft.

### 5.3 Protocol

Pre-flight, in writing, completed before the game is touched:

1. Both machines: same overlay, connected, version shown; `Ping host` succeeds.
2. Both machines: Blur installed and launched once so its Windows Firewall rule
   exists (host *and* player need it — the host must be able to answer).
3. Host: create the LAN lobby, note the lobby name and the time.
4. Host: start Host mode; confirm `forwards heard` reads 0 and the status is
   "waiting".
5. Player: start the bridge; confirm `captured` increments when Blur's Find Game
   screen is opened or refreshed.

Run order:

6. Player refreshes Blur's LAN list. Host watches `forwards heard`.
7. Answer (a) from the host's counter; if zero, stop and diagnose the tunnel
   before spending the rest of the window.
8. Answer (c) by observation: does the lobby list on the player, does a join
   complete.
9. Answer (b) from the player-side capture, whether or not the lobby appeared.

### 5.4 Criteria fixed in advance

Written before the run so the evidence decides, not the mood afterwards:

- **(a)** answered **yes** when `forwards heard ≥ 1` within 60 s of a refresh;
  **no** when a confirmed-working bridge produces no forward across two
  refreshes.
- **(b)** "dials the physical endpoint" when the player sends anything to the
  host's embedded physical address on `3074` and nothing to the overlay one;
  "dials the overlay" when the reverse; "neither" when the player sends nothing
  to either, which leaves the question open rather than answered.
- **(c)** answered by what is on screen, with the time noted.

### 5.5 The inconclusive branch

Historically Blur answered exactly one injected query and stayed silent
afterwards. A silent host is therefore a **likely** outcome and is recorded as
**inconclusive, never failed**.

Retry protocol (fixed in advance): up to three attempts in one sitting; each
attempt creates a fresh lobby and injects during the short window right after
entering the host screen, which is the timing that once produced an answer. If
all three are silent, the recorded finding becomes "not reproducible on demand",
with the note that real use is unaffected because a searching Blur queries
continuously — the injected-query experiment is not the same shape as a real
searching player.

### 5.6 The decision gate

| Evidence for (b) | Outcome |
|---|---|
| Player dials the **physical** endpoint and the join fails | Gate **opens**: offset-exact, length-preserving reflection becomes a workstream, off by default, enabled only with explicit per-session consent, with a `SECURITY.md` entry and its own tests. The "no payload rewrite, ever" sentence is amended, not deleted |
| Player dials the **overlay** endpoint | Gate **closes for V2**: the promise stands untouched, and the finding is recorded as the reason no rewriter exists |
| Player sends nothing to either | **Neither**: recorded open, with the exact next step (host-side capture of the join attempt), and no rewriting work starts |

### 5.7 Artifacts

Both logs, both captures, an outcome table in the style of the existing
injection/answer table in `docs/packet-research.md`, and the decision recorded in
`packet-research.md` and `TODO.md`. Screenshots stay out of the repository unless
scrubbed.

## 6. Architecture

```
                        BlurLink.Desktop  (Avalonia 12, net10.0-windows)
        ┌──────────────────────────────────────────────────────────────┐
        │  Views      Join | Host | Diagnostics | Settings             │
        │                    ▲ projections only                        │
        │  SessionState ◄─────┴──── SessionStory  (plain language)     │
        └───────────────┬──────────────────────────┬───────────────────┘
                        │                          │
        BlurLink.Core   │  SessionCoordinator ─────┘   ← the only helper talker
                        │      consumes status → produces state + story
                        ▼
        IPlatformServices (Windows impl)   IHelperClient ──► named pipe
                        │
        BlurLink.Net    blurlink-net.exe (elevated, WinDivert) — unchanged
```

### 6.1 What stays

`Contracts`, `Core`'s existing units (validators, filter builders, packet
transformer, rate limiter, diagnostics, logging), `Net` and `tools/hostsim` are
carried over unchanged apart from the `ifIdx` term (§7.5).

### 6.2 The session state model (`Core`)

One type owns the truth and one coordinator owns the helper.

- `SessionState` — mode (none, sniff, bridge, host), phase (idle, starting,
  running, stopping, failed), and a facts block: counters, roster, active filter,
  blocking reason, last error, capability flags (helper present, driver loadable,
  overlay address known, adapter selected, game running).
- `SessionCoordinator` — the only code that talks to `IHelperClient`. It consumes
  the status messages the helper already sends, owns stale-token and dead-helper
  handling, and produces the state above.
- `SessionStory` — the user-visible reading of that state: a decision table over
  (mode, phase, counters, capabilities) yielding a sentence plus a suggested
  action. It contains no UI types and no string-building elsewhere in the app.

**Why this is the keystone.** Today the equivalent logic is scattered through a
1,261-line view model, so "what should the user be told" cannot be tested and
drifts. As a table it gets table-driven tests: **every user-visible sentence has
a test asserting the state and counters that produce it**, including the
ambiguities V1 documented by hand — `forwards heard == 0` also means "your friend
has not announced yet", and it must not claim otherwise.

### 6.3 Platform seam

One interface for the genuinely Windows parts: single-instance guard, helper
extraction and staging, process watching, adapter enumeration, log paths. One
Windows implementation. The seam exists so the state model and view models can be
tested without Windows-specific machinery, not to prepare a port (D3).

### 6.4 The Avalonia shell

Four destinations — Join, Host, Diagnostics, Settings. Hand-written MVVM with the
existing base class and a plain composition root; **no DI container and no MVVM
toolkit** (D8). View models are projections of `SessionState`; no view owns
session logic.

### 6.5 Packaging

- Deliverable: slim framework-dependent single-file, helper and WinDivert
  embedded and staged on first launch, as today.
- Spike: NativeAOT single-file flavor as the no-runtime path, measuring real
  size and verifying helper staging and elevation still work. Avalonia's XAML
  makes trimming fiddly, which is why the spike result does not gate the release
  (D10).
- Retire `-Full` / `-Sfx` when the spike delivers (D12).

## 7. User-facing behaviour

### 7.1 Guided first run

Four steps, each with plain-language failure text:

1. **Find Blur** — detect the installation (known Steam/registry paths) and the
   running process; offer to launch it.
2. **Choose the overlay** — pick the adapter, confirm the local overlay address,
   run the existing route check.
3. **Verify the discovery port** — listen ~15 s while the user refreshes the
   game's LAN list, then write a **dated verified profile**. As part of this the
   tool re-checks the payload prefix across captures and records it only if
   three or more agree (the existing stability rule), so the profile is written
   from evidence rather than from a constant.
4. **Pre-flight** — ping the host address, confirm the firewall rule exists for
   Blur, and state any failure with the fix rather than the symptom.

Outcome: a profile with a verified badge, and Join mode **startable by default**.
Research mode survives as *Advanced: manual profile entry* and is no longer what
a newcomer meets.

### 7.2 Plain-language status

Rendered from `SessionStory`, with the raw counters one disclosure away so the
honest engineering stays visible. Examples of the mapping:

| State | What the user reads |
|---|---|
| Bridge running, nothing captured | "Nothing captured yet — open Blur's LAN browser and refresh the server list." |
| Bridge running, forwards sent | "You are reaching the host. If the lobby does not appear, the host may need Host mode." |
| Host running, `forwards heard == 0` | "No player has announced itself yet. Nothing is wrong until someone searches for your game." |
| Host running, forwards heard, replies forwarded | "Your reply is being sent back over the overlay." |
| Helper lost | "Lost connection to the helper" plus the recovery action, as today |

### 7.3 Support tooling

One-click **support bundle**: logs plus diagnostics metadata, zipped, with the
existing metadata-only logging discipline and a guard that proves no payload
bytes can enter it. Local crash capture for unhandled exceptions. The log viewer
moves under Diagnostics.

### 7.4 Everyday polish

Tray icon reflecting session state; notifications for lobby detected, session
stopped and helper lost; remembered per-profile settings; the existing
attach-to-Blur and auto-stop behaviour unified with the launch flow.

### 7.5 Deeper correctness

- **`ifIdx` term in the filters** so the adapter picker actually constrains
  capture. Covered by the existing filter-builder tests and asserted by the
  harness's reported-filter stages.
- **Reply-shape validation, observe-only** (D11): replies are checked against the
  verified profile (length, leading run, nonce echo) and mismatches are reported
  and counted, never silently forwarded, never blocked.
- **Verify this profile** — re-runs port detection and prefix stability, compares
  against the stored profile, shows the evidence, and can write
  `profiles/blur-lan-verified-<date>.json`. This is how the file `TODO.md` has
  wanted since V1 finally gets produced.
- **Refusal reasons readable** — broadcast, dedup, rate-limit and payload-gate
  refusals shown as counted, explainable events rather than numbers.

### 7.6 Accessibility baseline

New views meet a floor, not a project: keyboard reachability for every action,
sensible focus order, and accessible names on interactive controls.

## 8. Engineering completeness

### 8.1 Version control and the privacy scrub

`git init`, a `.gitignore` covering `bin/`, `obj/`, `out/`, `dist/` and the
third-party binaries (the SHA256 pins in `third-party/WinDivert/README.md` are
the record), then an initial commit and a public GitHub repository.

Before the first public push, a scrub with one rule: **structure, offsets and
byte layout stay; identifiers are replaced.** It covers real LAN and overlay
addresses, the overlay network name, process IDs — and the host name `Mani`,
which is embedded in the captured reply payload as UTF-16 (`4d0061006e0069`) and
therefore present in the docs as raw hex. Raw captures stay out of the repository
(`out/` is ignored); only scrubbed excerpts enter the docs.

### 8.2 CI jobs (GitHub-hosted Windows)

| Job | Purpose |
|---|---|
| managed | restore, build, `dotnet test` on .NET 10 |
| native | CMake build, `ctest`, `scripts/test-interop.ps1` |
| driver harness | the M0 experiment; if it works it becomes a scheduled job, if not the failure and reason are recorded |
| UI | Avalonia headless UI tests over the view models and views |
| docs | docs-consistency checks (§8.5) |
| package | build the portable, assert it launches with the helper embedded |
| release | on tag: build, zip, hash, attach, include notices |

### 8.3 Test layers

Unit (including `SessionStory`'s decision tables), IPC contract, native, headless
UI, live interop, driver harness, docs. `scripts/test.ps1` runs everything that
needs no elevation; the elevated scripts gain a **preflight-only** mode so the
environment checks are runnable and testable without admin.

### 8.4 Release process

Tag → CI builds the portable → zipped with `LICENSE`, `THIRD-PARTY-NOTICES.md`
and SHA256 hashes → attached to a GitHub release → README states the verified
status honestly. winget deferred (D6).

### 8.5 Docs cannot silently drift

A small **retracted-claims registry**: statements that were withdrawn (starting
with "a hosting Blur is silent") plus the phrase that must not reappear outside
their retraction note. A script fails CI when a registered claim is asserted
elsewhere, and cross-checks documented constants (defaults, ports, sizes) against
the code.

## 9. Milestones

**M0 — Foundation.** Exit criteria: repository exists with the scrub applied and
its first commit containing this spec; .NET 10 upgrade done; CI green on the
existing tree; docs check added; the driver-harness experiment run with its
result recorded.

**M1 — Evidence.** Exit criteria: the prep in §5.2 built (correlated timestamps,
player-side capture filters, written protocol); the session run; the outcome
table recorded; (a), (b) and (c) each marked answered or open with the reason; the
gate in §5.6 applied and the decision written into `packet-research.md` and
`TODO.md`. If the gate opens, the reflection workstream is added with its own
design note, `SECURITY.md` entry and tests.

**M2 — Engineering.** Exit criteria: `SessionState`/`SessionCoordinator`/
`SessionStory` in `Core` with decision-table tests; docs-consistency checks live
in CI; the harness either in CI or with the documented fallback in place; the AOT
spike measured and recorded; release automation proven by a dry-run tag.

**M3 — Surface.** Exit criteria: Avalonia shell at feature parity with WPF
(single instance, attach, stop semantics, settings import/export, log viewer);
`JoinViewModel` no longer exists as a monolith; the four feature bundles in the
order given (status and first run, verify-profile, support bundle, polish, then
the correctness extras); headless UI tests covering every view; accessibility
floor met.

**M4 — Release.** Exit criteria: tagged release downloadable with hashes and
notices; README rewritten around what is verified and what remains open; the WPF
project removed from the solution.

M1 is the only externally gated milestone, so the implementation plan is
expected to stage these as separate plans (M0+M2 together, M1 whenever the
session window opens, then M3, then M4) rather than one continuous run.

## 10. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | The evidence session is inconclusive (Blur stayed silent historically) | §5.5 retry protocol; "inconclusive, never failed" recording; the note that real use is unaffected because a searching Blur queries continuously |
| R2 | The second machine is not available when needed | The session is the only externally gated workstream; M0 and M2 proceed regardless. A rented cloud Windows machine stays a contingency, not a plan |
| R3 | The Avalonia port grows beyond its box | State model built and tested first; WPF app stays shippable until parity; no feature work on WPF except security fixes |
| R4 | Trimming/AOT with XAML is fiddly | Spike early in M2; slim framework-dependent remains the deliverable so the release never depends on the spike |
| R5 | The driver-harness experiment fails on hosted runners | The documented fallback is the manual-but-provable protocol; self-hosted and cloud options are left as a decision to be made on that evidence |
| R6 | The privacy scrub damages evidentiary value | Scrub is a reviewed diff with the §8.1 rule; offsets and structure preserved; raw captures never enter the repository |
| R7 | Scope is large | The strict sequence (D9) and the fixed order inside M3; `SessionStory` is the first M2 deliverable because everything user-visible depends on it |
| R8 | The gate opens and reflection turns out to be harder than it looks | It stays a consent-gated workstream with its own design note; nothing else in V2 depends on it |

## 11. Success criteria

1. A newcomer on a clean Windows machine gets a lobby without reading any
   documentation.
2. Every push runs unit, native, interop, headless UI and docs checks, and the
   driver harness if M0 proved it possible.
3. The two-machine evidence table is complete, and each question from §5.1 is
   either answered with evidence or marked open with its next step.
4. A tagged release exists, downloadable, with hashes, notices and an honest
   README.
5. Every user-visible status sentence is produced by a tested decision table.

## 12. Open questions for the implementation plan

Each has a decision rule; none blocks the design.

| # | Question | Settled by |
|---|---|---|
| Q1 | Exact retry count and window length for §5.5 | Decided when writing the session checklist; the current proposal is three attempts in one sitting |
| Q2 | Whether the driver-harness CI job runs per-push or on a schedule | The M0 experiment result: per-push if it is fast and deterministic, scheduled or manual if it is flaky |
| Q3 | The verified profile's payload prefix: 3 bytes (`0F0000`) or the full stable 12-byte leading run | The verify-profile tool's stability check at implementation time, per the existing three-capture rule |
| Q4 | Whether reply-shape validation ever progresses from observe-only to enforcing | A second independent capture agreeing on the reply's stable fields, plus a decision in review |
| Q5 | The consent UX if the rewrite gate opens | Part of the conditional reflection design note; must be per-session and revocable, never a saved-on default |
| Q6 | Whether the AOT flavor becomes the default deliverable | The M2 spike: size, startup, and whether helper staging and elevation survive |
| Q7 | Which of `-Full` / `-Sfx` is removed first | M4, once the AOT flavor is proven or dropped |
